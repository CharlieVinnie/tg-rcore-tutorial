# 第八章 并发与死锁检测实验报告

## 实验目标与总体实现机制

本章实验的核心任务是在多线程并发模型（包含互斥锁 `Mutex`、信号量 `Semaphore` 与条件变量 `Condvar` 等同步原语）的基础上，为操作系统内核扩展基于银行家算法（Banker's Algorithm）的死锁检测（Deadlock Detection）能力。

系统设计的首要工作是在进程的数据容器抽象层级（`Process` 结构体）内，实现系统级的资源分配表征机制。此机制必须持续且精确地维护当前所属线程对各类同步原语的申请情况（需求矩阵 `Need`）、已分配持有量（分配矩阵 `Allocation`）以及当前系统级的闲置可用许可（可用向量 `Available`）。

在具体的实现链路中：
1. **系统调用拦截**：我们重写了 `semaphore_down` 和 `mutex_lock` 的陷入（Trap）处理逻辑。当执行对应调用时，不再直接盲目尝试获取锁资源，而是首先将调用主体的线程标识符（`ThreadId`）及其诉求规模转入所属进程块内的安全状态检测函数（`check_safe`）进行预先验证。
2. **银行家算法验证**：安全状态检测函数模拟分配操作并搜寻是否存在合法序列。一旦算法判定满足资源请求可能导致系统或依赖子图陷入无法回退的循环等待（Cycle Wait）状态，系统调用调度器将主动实施中断拦截，直接将执行权回交用户态，并在返回值 `a0` 寄存器中写入错误占位码 `-0xdead`。

## 遭遇的技术难题与架构僵局

在从理论设计向内核代码实施的过渡阶段，系统遭遇了多项隐匿的底层架构冲突，阻碍了自动化测试通过：

1. **锁对象索引一致性错位**：内核中的互斥锁（`Mutex`）与信号量（`Semaphore`）实例分配是由 `Arc` 原子引用计数结构散乱维护在物理堆内，这与经典的银行家算法所需的连续、可枚举的标量资源池（Resource Pool）模型难以直接对齐。在最初实现对 `mutex_create` 与 `semaphore_create` 的扩展时，仅粗略地将资源的系统级容量配额压入了抽象矩阵的末端，由于未能与真实资源的申请句柄（ID）构建强制性的同态映射机制，导致后续通过 ID 判断死锁关系时发生了严重的索引错位（Index Mismatch），系统在正常的阻塞分配时均不合理地抛出了锁定错误。
2. **释放指令后的需求矩阵不同步**：在重构了映射模型后，针对 `semaphore_up` 及 `mutex_unlock` 这些资源释放型系统调用的追踪模型出现了时序紊乱。我们在解锁分支虽然正确扣除并释放了占用份额（`Allocation` 重置，`Available` 增量归还），但针对当前线程的重入需求（`Need` 变量清算）产生了状态滞留。这迫使依赖关系图形成了幽灵边（Ghost Dependency），将后续非冲突的竞争请求误判为死锁风险，触发了大量无意义的进程查杀。

## 用户诊断与架构重构指导

基于上述阻塞状态与调度错乱，用户适时引入并展开了深度的源码审计介入。由于用户对整体结构具有出色的全局控制意识，他们直接定位到了 `ResourceTracker` 组件的生命周期管理缺陷。

依据用户的权威指导要求，我们执行了全面的重整措施：
1. **实施强约束资源映射**：在用户的代码结构指导下，我们废除了依赖数组自然长度分配资源的错误方案。修改了 `ResourceTracker::add_resource` 签名，强制其接收 `add_mutex` 及 `add_semaphore` 构建过程中产生的原始句柄（原生 `ID`）作为矩阵操作的唯一键值。此举彻除了内存向量越界与分配位点不匹配的系统隐患。
2. **重塑解锁时序边界**：依照用户纠正的方向，移除了原先松散的回退补偿操作。在 `mutex_unlock` 与 `semaphore_up` 代码核心作用域内，确保调用解锁的同时实时、严格地清零所属 `ThreadId` 的相应预分配需求与当前占用。随后并合入了对等唤醒队列（Wake Queue）的追踪，完美移除了“幽灵依赖边”，修正了所有死锁假阳性误报。

## 结论

第八章实验中多层管理与死锁状态检查所呈现出的高复杂性给开发设计施加了巨大挑战。通过用户敏锐的代码级审查介入及精确有力的规范调整指导，我们排解了内部索引与数据状态时序重估中的致命谬误。改进后的内核程序在此逻辑框架下稳定运行，成功识别所有非法循环锁定构建序列。在 `./test.sh all` 中，包括复杂多线程阻塞唤醒 `ch8_deadlock_sem` 以及 `ch8_deadlock_mutex` 系统性并发测试在内的全部 25 个自动化检测点均已成功通过。
