# 第四章 虚拟内存与实验练习重构报告

## 实验背景与初始实现策略

本章节的核心编程任务是在引入 RISC-V Sv39 虚拟内存机制的基础上，实现 `mmap` 与 `munmap` 内存管理机制，并重构 `sys_trace` 系统调用使其兼容独立的虚拟地址空间。

在初始的实现方案中，我们采取了以下策略：
1. **进程状态追踪**：在 `Process` 结构体中新增了 `syscall_counts` 数组，用于记录隔离的单进程系统调用统计信息。
2. **虚拟地址翻译**：在 `sys_trace` 针对内存读取和写入的操作中，引入了 `process.address_space.translate`。不仅对 `Sv39` 的地址合法性进行翻译，并结合 `_RV` 与 `_WRV` 权限位严格验证了用户态页表映射的读写权限。
3. **动态内存映射**：在 `sys_mmap` 与 `sys_munmap` 中，通过检查地址的按页对齐原则，通过调用底层虚拟内存空间的映射树结构进行分配与回收操作。

## 遭遇的技术瓶颈与初期架构折衷

在实现 `sys_trace` 的功能分支时（即 `trace_request == 2` 查询系统调用计数的逻辑），我们在架构层面遇到了一处设计壁垒：
系统调用的接口层 `impl Trace for SyscallContext` 被设计为高度解耦的执行上下文实体。在设计初期，我们误判了执行层获取全局进程管理器上下文引用的难度与安全性，认为在此隐式上下文中直接越级读取底层 `Process` 数据可能会引发复杂的作用域和借用冲突原则。

为了迅速绕过这一访问限制，当时的方案采用了一种应急的**拦截式架构**：
在 `impl Trace for SyscallContext` 内部，针对 `trace_request == 2` 的调用仅作 `-1` 或 `0` 占位处理。真正的业务逻辑被“硬编码”强行塞入了系统内核主循环的系统调用触发分发器（即 Trap 分发 `tg_syscall::handle` 的后续执行阶段）中。通过侦测寄存器，直接覆写进程返回上下文内寄存器 `a0` 的最终返回值。虽然能够通过单元测试代码，但这使得系统调用的执行逻辑出现了严重的越界与高强度耦合。

## 用户的纠正指导与最终重构

在此过程中，用户的敏锐观察起到了决定性的作用。用户准确指出了内核主处理循环中的异常代码块，并提出质询：为何将针对特定系统调用的逻辑直接堆砌于主调度循环中，而非放置于标准的 `impl Trace for SyscallContext` 接口实现块之下？

在用户的指导下，我们重新审视了上下文对全局进程数据结构 `PROCESSES` 的访问能力，并确认可以直接通过 `caller.entity` 参数提取并索引至正确的全局数据节点，无需在此处顾虑借用冲突。

相应的重构工作如下：
1. **剥离调度器耦合**：彻底删除了内核事件主循环内，所有专门针对 `sys_trace` 的特判拦截代码块，恢复了系统调用执行完毕即刻恢复 `sret` 的原生调度链路。
2. **职责回归本源**：将 `trace_request == 2` 的数组查询判定业务，完完整整地移回至 `impl Trace for SyscallContext` 代码块内部。
3. **安全寻址**：利用原生的 `unsafe { PROCESSES.get_mut()[caller.entity].syscall_counts[id] }` 直接并安全地从内核态准确抓取了待查询的请求数量。

## 总结

综上所述，本次实验的核心难点在于理解并执行上下文穿透和虚实地址跨界翻译的要求。在应对由架构拆分造成的结构断裂时，初始方案曾陷入破坏高内聚原则的误区。最终在用户严谨直接的代码审查与修正指导下，系统成功剔除了不合理的硬编码机制，将 `sys_trace` 剥离回其应当存在的层级，确保了模块代码的高度规范一致性。回归测试（`./test.sh exercise`）的全面通过亦证实了此次重构的安全与稳定。
