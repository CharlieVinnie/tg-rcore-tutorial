# 第五章 代码阅读指南：进程

本章在虚拟内存隔离的基础上，引入了操作系统最核心的动态实体抽象——进程（Process）。本章系统由静态装载的单一应用执行模型，正式越迁至具备动态分支、程序替换及层级式生命周期管理的完备进程树模型。

阅读本章时请关注两大主线：一是代表单个进程运行快照的 `Process` 实体的演替逻辑；二是代表全局控制中枢的调度机制演进。

## 1. 原生进程初始化

操作系统的第一个生命不借由克隆而生，而是由内核手工雕刻，此即为初始进程（`initproc`）。

### 1.1 `tg-rcore-tutorial-ch5/src/main.rs` (第 1 处)
**阅读范围：** `rust_main` 内步骤 8，加载初始进程 `initproc`。
```rust
    let initproc_data = APPS.get("initproc").unwrap();
```
本章由于启用了 `tg_task_manage::ProcId` 作为身份标识系统，原先直接暴露于主函数中的 ELF 遍历加载逻辑被抽象至单例初始化模式。内核依靠查表获取名为 `initproc` 的程序数据（此序即用户态系统初始化的起点），随后调用 `Process::from_elf` 方法将其转化为处于就绪阶段的内存实体，并首次分配全系统唯一的 `ProcId`。
接着，通过调用 `PROCESSOR.get_mut().add(...)`，此零图号实体被送入中央队列等待调度。

### 1.2 `tg-rcore-tutorial-ch5/src/process.rs` (第 1 处)
**阅读范围：** `Process::from_elf` 方法。
此方法系第四章沙盒装载逻辑的模块化封装：
1. 提取并验证 ELF 格式，确认入口地址。
2. 构造具备全新页表的地址空间，依 `Load` 属性循环装配应用段机制与各段权能。
3. 高位挂载并赋予用户权限的物理双页栈空间。
4. 全局共享映射传送门页表目录（`map_portal`）。
5. 返回装配了新虚拟页表地址指令（`satp`）并内置了唯一 PID 的完整进程对象。此后的任何独立运行控制都将建基于这一实体结构。

## 2. 全局管理与轮转调度

多个进程实体必须依托调度中枢方可实现 CPU 计算时间片的共享。

### 2.1 `tg-rcore-tutorial-ch5/src/processor.rs`
**阅读范围：** 整个文件，重点关注 `Processor` 及 `ProcManager`。
请转移至此模块观察调度结构的更迭：
```rust
pub struct ProcManager {
    tasks: BTreeMap<ProcId, Process>,
    ready_queue: VecDeque<ProcId>,
}
```
相较于早期简单的集合容器，本章引入了基于外部组件 `tg_task_manage` 的抽象特型（`Manage` 与 `Schedule`）。
为了实现高效的状态查询与 O(1) 的就绪序列剥离，结构采用 `BTreeMap` 以进程 ID 为键维系全量生命周期对象的物理存续，并辅以 `VecDeque` 实现经典基于先入先出（FIFO）语义的公平时间片轮转（RR）调度队列。此两面性结构（数据持存面与算法调度面）也是未来向诸如 Stride 等高级调度算法演进的重构接口面。

### 2.2 `tg-rcore-tutorial-ch5/src/main.rs` (第 2 处)
**阅读范围：** `rust_main` 函数尾段的主调度循环 `loop { ... }`。
该无限循环构成了操作系统的心跳：
1. `(*processor).find_next()`：探针从就绪队列头部摘取控制权块。
2. `ctx.execute(portal, ())`：执行流沿传送门陷落至特定的 U 态逻辑域（参见第四章第 4 节之机制重溯）。
3. 因外围硬件中断（时钟抢占）或内部软陷阱（系统调用指令）导致程序重夺控制权后，逻辑分流。若进程仅为时间片耗尽或发生不涉及生命周期完结的正常系统通信，其状态流将由 `make_current_suspend()` 更新（该函数会将其压回就绪队列尾部等待下一次调度轮回）。

## 3. 动态生命周期：进程分蘖与替换

现代操作系统的进程管理高度依赖繁衍与重载这两种正交语义的结合（即 `fork` 与 `exec`）。

### 3.1 `tg-rcore-tutorial-ch5/src/impls.rs` (进程模块系统调用实现)
**阅读范围：** `Process` 特型对 `SyscallContext` 及其内联方法的实现逻辑（特别关注 `fork` 与 `exec`）。

#### 3.1.1 `fork` 的控制流裂变
```rust
    let mut child_proc = current.fork().unwrap();
```
当应用发起 `fork` 调用求取克隆体时，进入调用链深层 `process.rs` 的 `fork()` 方法。
内核将发起极度耗时的**地址空间深拷贝**：不仅再造 Sv39 页表树形拓扑结构，更会分配崭新且毫无重叠的等量物理页块，将被克隆者的所有可读写静态段及运行时栈、堆数据实行逐字节重制（`cloneself`）。同时完整装填包含原返回地址（`sepc` 寄存器等）的用户态寄存器阵列备份。
待拷贝流返回 `impls.rs` 时刻：
1. 框架赋予此副本新的 PID 并写入进程管理层树的子节点位以待派发。
2. 异常关键的补丁操作：`*context.a_mut(0) = 0`。框架篡改该副本用作接收返回值的寄存器参数，使其在恢复执行时伪饰出 `0` 的回执结果。原进程继续持有原始执行栈路径，被塞入新产生的子体 PID 进行后续流转。这构成了 “一次调用，两个截然不同路径返回” 的操作基础。

#### 3.1.2 `exec` 的破壳置换
```rust
    current.exec(data);
```
用户应用在发觉自身处在被 `fork` 分离的 0 值支路后，通常随即呼叫 `exec` 系统调用。
此阶段内核从自身持有的 `APPS` 文件系统抽象镜像中搜刮出与传入名符字符串匹配的目标 ELF 流。在执行权限校验通过后，直接丢弃该拷贝进程的旧有 `address_space`（深拷贝心血在此刻全盘废除，原物理页将被 Rust Drop 体系回收），在**留存原 PID 枢纽地位绝对不变**的严格指令下，通过新 ELF 解析重构一片完全陌生的段映射体系、崭新的入口点 `sepc` 与高位起始的用户新栈。
进程自此褪去了前身的旧壳，以相同的注册身份迎来了全新的运行代码序列指令。
